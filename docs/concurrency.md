# 동시성 제어

재고는 여러 사람이 동시에 건드립니다. 관리자 두 명이 같은 품목을 고치고, 작업자가 실사하는 사이 출고가 일어나며, 창고 음영 지역에서 센 수량은 나중에 한꺼번에 올라옵니다. SoG는 이런 경쟁을 다섯 겹으로 다룹니다.

| 겹 | 어디서 | 무엇을 막나 |
|---|---|---|
| 1. 낙관적 잠금 (ETag · If-Match) | 데모 서버 | 다른 사람의 저장을 모르고 덮어쓰기 |
| 2. 쓰기 직렬화 (Web Locks / Postgres 트랜잭션 잠금) | 업무 서버 | 탭·기기·함수 인스턴스가 동시에 읽고-계산하고-쓰다 재고가 음수가 되거나 두 번 반영 |
| 3. 멱등 키 (Idempotency-Key) | 업무 서버 · 클라이언트 | 응답을 못 받고 다시 보낸 요청의 중복 반영 |
| 4. 실사 정산 규칙 | 도메인 | 실사 도중 일어난 입출고의 이중 반영 |
| 5. 재고 예약 | 업무 서버 | 두 출고 지시가 같은 마지막 재고를 동시에 잡는 일 |
| 6. 화면 쪽 경쟁 | 두 앱 | 빠른 연속 클릭, 늦게 도착한 검색 응답, 수정 중 들어온 다른 탭의 변경 |
| 7. 접속 표시 (presence) | 두 앱 | 같은 자원을 동시에 고치거나 세는 일 자체를 미리 피함 |

## 업무 서버

업무 규칙은 `packages/wms-server` 한 곳에 있고, 운영에서는 Postgres 위의 Vercel 함수로, 개발·미리보기에서는 브라우저 안(IndexedDB)에서 돌립니다([실제 서버](backend.md)). 어느 쪽이든 같은 HTTP 의미를 지켜, 앱은 `HttpClient`로만 통신합니다.

- 연결: `@sog/wms-client`의 `wmsInterceptor`가 `/api/**` 요청을 실제 서버나 브라우저 안 데모 서버로 보냅니다.
- 데모 모드의 응답 지연: 120~450ms를 일부러 넣어 경쟁 상태가 실제로 생기게 합니다.
- 두 앱 데이터 공유: 백오피스는 `/`, 실사 앱은 `/count/`에서 열려 출처가 같습니다. 데모 모드에서도 같은 브라우저의 두 앱이 데이터를 나눠 씁니다.

### 1. 낙관적 잠금

수정할 수 있는 자원(품목, 로케이션별 재고, 실사 작업, 실사 항목)은 모두 `version`을 가집니다.

```
GET  /api/skus/sku-10201        → 200, ETag: "3"
PATCH /api/skus/sku-10201       If-Match: "3"  → 200, ETag: "4"
PATCH /api/skus/sku-10201       If-Match: "3"  → 412 VERSION_CONFLICT, current: { 최신 자원 }
PATCH /api/skus/sku-10201       (If-Match 없음) → 428 PRECONDITION_REQUIRED
```

412 응답에는 최신 자원을 담아, 화면이 다시 조회하지 않고 바로 비교할 수 있게 합니다. 막아 낸 충돌은 활동 기록과 품목의 변경 이력에 막힌 값과 함께 남아, 나중에 그 값을 다시 불러올 수 있습니다.

화면의 처리:

- **품목 정보 수정**(`features/edit-sku`): 내 입력과 최신 값이 다른 항목만 표로 보여 주고, "내 입력으로 다시 저장"(최신 버전 기준으로 다시 보냄)과 "최신 값 불러오기" 중에서 고르게 합니다.
- **재고 조정**(`features/adjust-stock`): 그사이 바뀐 장부 수량을 보여 주고 다시 확인을 받습니다.
- **실사 승인·취소**(`features/review-count`): 작업자가 더 셌거나 다른 관리자가 먼저 처리했으면 최신 상태를 다시 받습니다.
- **현장 실사**(`entities/outbox`): 관리자가 재실사를 요청해 항목 버전이 올라가면, 보낼함의 기록은 덮어쓰지 않고 "확인 필요"로 남아 작업자가 다시 셉니다.

### 2. 쓰기 직렬화

모든 쓰기는 잠금 안에서 읽고, 검사하고, 한 트랜잭션으로 씁니다. 그래서 두 사람이 같은 재고를 동시에 출고해도 가용 재고 검사와 차감 사이에 다른 쓰기가 끼어들지 못합니다.

- 데모 모드: `navigator.locks.request('sog-wms:write', { mode: 'exclusive' })` + IndexedDB 트랜잭션(`lock.ts`, `idb.ts`)
- 실제 서버: Postgres 트랜잭션 + `pg_advisory_xact_lock`. 잠금 안의 읽기·쓰기·변경 기록이 같은 연결을 써서 함께 반영되거나 함께 취소됩니다(`pg-backend.ts`).

- 출고·이동은 가용 재고(보유 − 출고 지시)를 넘으면 409 `INSUFFICIENT_STOCK`.
- 이동은 출발지와 도착지를 한 트랜잭션으로 바꿔 총량이 보존됩니다.
- 새 실사 작업은 진행 중인 다른 실사에 들어 있는 재고를 빼고 만듭니다(같은 재고를 두 작업이 세지 않게).

Web Locks가 없는 환경(Node 테스트)에서는 이름별 큐로 대신합니다. 테스트는 같은 DB를 여는 서버 두 개로 "탭 두 개"를 만들어 동시 출고 중 하나만 성공하는지 확인합니다.

### 3. 멱등 키

`POST /api/movements`, `POST /api/counts`, `PUT /api/counts/:id/lines/:lineId`는 `Idempotency-Key`를 받습니다. 같은 사용자·같은 대상·같은 키면 처음 응답을 그대로 돌려주고(`Idempotent-Replayed: true`) 재고는 바꾸지 않습니다.

- 백오피스 입출고 폼은 열 때 키를 하나 만들어, 실패 후 다시 눌러도 같은 키를 씁니다.
- 실사 앱 보낼함은 기록마다 키를 붙여, 보내던 중 앱이 닫혔다 다시 열려도 한 번만 반영됩니다.

### 재고 예약(출고 지시)

출고 지시를 만들면 잠금 안에서 최신 재고로 가용 수량(보유 − 출고 지시)을 다시 계산해, 가용 재고가 많은 로케이션부터 예약합니다(`allocate`). 모자라면 409와 함께 품목별 지금 가용 수량을 알려 줍니다. 두 관리자가 마지막 재고로 동시에 출고 지시를 만들면 한쪽만 예약되고, 다른 쪽은 부족 안내를 받습니다. 예약은 출고를 확정할 때 집은 만큼 재고에서 빠지고, 덜 집은 수량과 취소한 출고 지시의 예약은 풀립니다. 재고 조정은 예약된 수량 아래로 내릴 수 없고, 실사 승인도 확정 수량이 예약보다 적은 품목이 있으면 409로 막습니다(출고 지시를 먼저 조정하거나 재실사).

### 4. 실사 정산

실사는 시간이 걸리고 그동안에도 입출고가 일어납니다. 각 실사 항목은 만들 때의 장부 수량(`expectedQty`)과 재고 버전, 센 시각(`countedAt`)을 기록합니다.

```
승인 시 재고 = 센 수량 + (센 뒤에 일어난 입출고의 순증감)
```

센 수량은 센 시점의 진실이므로, 그 뒤의 이동만 위에 더합니다. 검토 화면은 항목마다 "실사 중 이동"과 "승인 시 재고"를 보여 주어, 관리자가 승인 전에 결과를 확인합니다(`settledOnHand`, `movementEffect`).

## 화면 쪽

### 중복 제출

`SubmitLock`(`packages/wms-client/src/http.ts`)은 동기 플래그로 두 번째 호출을 바로 버립니다. 신호(`pending`)는 다음 렌더에야 바뀌어 빠른 연속 클릭을 못 막기 때문입니다. 저장 후 화면을 떠나는 폼(입출고 등록, 실사 작업 만들기, 수량 저장)은 `keepLockedOnSuccess`로 성공한 뒤에도 잠그고, 실패하거나 입력이 잘못되었을 때만 풉니다. 두 앱 모두 더블 클릭 테스트로 확인합니다.

### 늦게 도착한 응답

목록 조회는 `httpResource`로 합니다. 검색어나 필터가 바뀌면 이전 요청을 취소하고, 인터셉터는 취소된 요청의 응답을 버립니다. 검색어는 `debounced()`로 0.3초 기다렸다 보냅니다. 다시 불러오는 동안에는 `linkedSignal`로 이전 결과를 흐리게 남겨 화면이 깜빡이지 않습니다.

### 다른 탭의 변경

서버는 쓰기가 끝나면 바뀐 자원의 주제(`skus/sku-10201`, `counts/ct-003` 등)를 알립니다. 데모 모드는 `BroadcastChannel`, 실제 서버는 순번이 붙은 변경 피드(`/api/changes`)로 다른 기기까지 전합니다. 화면은 `WmsHost.onChange`로 관심 있는 주제만 받아 다시 불러옵니다.

- 수정 중이 아니면 최신 값으로 바로 바꿉니다.
- 수정 중이면 입력을 지키고 "방금 수정했습니다" 안내만 띄웁니다. 그대로 저장하면 1번 충돌 처리로 이어집니다.
- 실사 검토 화면은 현장 앱에서 셀 때마다 표가 바뀌고 방금 바뀐 줄을 잠깐 강조합니다.

### 접속 표시

충돌을 잘 처리하는 것보다 충돌이 나지 않는 편이 낫습니다. `Presence`(`packages/wms-client/src/presence.ts`)는 탭마다 지금 보고 있는 자원과 상태를 5초마다 알리고(데모 모드는 `BroadcastChannel('sog-presence')`, 실제 서버는 `/api/presence`), 15초 동안 소식이 없거나 탭을 닫으면(`pagehide`) 목록에서 뺍니다. 서버 모드인지 알기 전에 서비스가 정리되면 서버 폴링을 시작하지 않습니다. 새로 연 탭은 `ping`을 보내 다른 탭의 현재 위치를 바로 받습니다.

- 품목 상세: 다른 관리자가 같은 품목을 보고 있으면 표시하고, 저장하지 않은 입력이 있으면 "수정 중"으로 강조합니다.
- 실사 상세: 현장 작업자가 어느 품목 앞에 있는지까지 보입니다.
- 현장 앱: 다른 작업자가 같은 품목 앞에 있으면 알려 같은 품목을 두 번 세지 않게 합니다.

접속 표시는 안내일 뿐 잠금이 아닙니다. 저장의 정합성은 여전히 1번 버전 검사가 지킵니다(비관적 잠금을 쓰면 탭을 닫지 않고 떠난 사람이 다른 사람을 막게 됩니다).

### 오프라인

실사 앱은 센 수량을 먼저 기기(IndexedDB `sog-count`)의 보낼함에 넣고, 연결되어 있으면 바로, 끊겨 있으면 다시 연결될 때 순서대로 보냅니다. 같은 항목을 다시 세면 보내지 않은 기록을 바꿉니다(마지막으로 센 값이 이깁니다). 바꾸기는 지우기와 쓰기를 한 IndexedDB 트랜잭션으로 해서, 새 기록을 못 쓰면 이전 기록이 남습니다. 배정된 진행 중 작업은 목록을 받을 때 뒤에서 미리 받아 둡니다. 다만 받는 도중 연결이 끊기면 일부 작업은 받지 못할 수 있으므로, 음영 지역에 들어가기 전에 필요한 작업을 한 번 열어 두는 것이 안전합니다.

## 직접 해 보기

1. 백오피스를 탭 두 개로 열고 한쪽은 김하늘, 다른 쪽은 박도윤으로 로그인합니다(비밀번호 `sog-demo`).
2. 같은 품목 상세에서 한쪽이 안전 재고를 고치는 사이 다른 쪽이 먼저 저장합니다.
3. 늦게 저장한 탭에서 충돌 비교표와, 아래 변경 이력의 막힌 시도를 확인합니다.
4. 실사 앱(`/count/`)에서 이서준으로 수량을 세면, 백오피스 실사 검토 화면이 새로 고침 없이 바뀝니다.
5. 실사 앱 설정에서 "오프라인 모의"를 켜고 세면 보낼함에 쌓이고, 끄면 자동으로 보내집니다.
